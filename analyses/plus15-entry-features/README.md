# +15 Entry Features

Collects price-action features at each 15m magnet close on 30s data and records the first-touch side within the +15 min window. Goal: discover which features actually predict *which side hits first* (since the magnet base rate just says *some* side gets hit).

## Files

| Path | Purpose |
|---|---|
| `pine/phase2_features.pine` | The TradingView indicator. Apply to a 30s chart. |
| `data/master_es.csv` / `master_nq.csv` | Growing, dedup-merged datasets. Source of truth for analysis. |
| `data/raw_*.csv` | One-time seed dumps. Not read by `analyze.mjs`. |
| `merge.mjs` | Appends a fresh table dump to master, deduping by (symbol, time_et). |
| `analyze.mjs` | Conditional analysis of features vs first-hit. Writes `FINDINGS.md`. |
| `FINDINGS.md` | Latest analysis report. Regenerated by `analyze.mjs`. |

## Daily collection workflow

TradingView caps 30s history at ~1.3 days. To not lose data, **read the table at least every 30 hours per symbol**. End-of-day after RTH close is the natural cadence.

For each symbol (ES1!, NQ1!):

1. In TradingView, set the chart symbol and confirm "Magnet Entry — Phase 2 (Features)" is applied on a 30s chart.
2. Read the indicator's table via MCP:
   `data_get_pine_tables` with `study_filter="Magnet Entry — Phase 2"`.
3. Pipe the table rows into the merger:
   ```sh
   pbpaste | node analyses/plus15-entry-features/merge.mjs ES1!
   ```
   or save to a temp file and:
   ```sh
   node analyses/plus15-entry-features/merge.mjs ES1! < /tmp/table.txt
   ```
4. The merger reports `+N new rows`. Most days N ≈ 80-95 (full day + Globex).

After both symbols are merged, regenerate findings:

```sh
node analyses/plus15-entry-features/analyze.mjs
```

## Why daily, not weekly

The Phase 2 table is a rolling FIFO of the last 120 events. ES + NQ each emit ~96 events/day (~4 events/hour × 24 hours of futures trading). So roughly:

- After 1 day: 96/120 events in buffer — safe.
- After 1.25 days: 120/120 events — buffer full, oldest events about to roll off.
- After 2 days: ~half the data is gone.

Daily cadence keeps overlap large (the merger handles dedup), so an occasional missed day still recovers everything.

## Tips

- If TradingView is closed for >30 hours, the next read will miss whatever rolled out of the buffer. That gap is unrecoverable.
- The indicator's `Max events in table` input can be raised (default 120). Higher = more slack between reads, but slower table serialization over MCP.
- If you switch the indicator's symbol but the table doesn't refresh, click any 30s bar to force a recompute, then re-read.

## Caveats baked into the data

- "First touch" is defined at 30s resolution. When both extremes wick in the same 30s bar, `first` is recorded as `ambiguous` and the analyzer drops those rows.
- All features are snapshot at magnet close *except* `drv` (opening drive at +90s). `drv` is not usable for a live entry that fires at the magnet close — treat it as a *post-hoc* feature to study, not a real-time signal.
- `htf` and `vwap` are computed on the security request; very-early bars in loaded history may have NaN context.
